## 1. 보내주실 것

- 참고로 이 저장소 코드로 계산한 P1 horizon별 오차(2024-01~2026-09, 거래일 기준)는 MAPE h=1 2.21% / h=3 3.75% / h=5 4.88%, σ(h) 3.3%→6.5%입니다. 현승님 2019~ 값(1.53/2.66/3.91)보다 큰 이유는 2024~26년 변동성이 더 컸기 때문이고, 두 값 모두 "정의가 다른 같은 결론"입니다.

## 3. 보고서 서술 확인

### 6. 안전계수 ×1.10/×1.05 → z = 0.4로 바뀐 이유
- 서술 맞습니다. 보충: 이론(임계비율 0.914)은 과잉 1개 비용을 보관비 $30으로만 봤는데, 실제로는 추가 생산분이 전부 **2배 잔업 구간**에서 만들어지고 다음 날에도 같은 잔업 구간이라 회수가 안 됩니다. 실제 비용표로 백테스트하면 품절 몇 %를 감수하는 쪽이 이익이 큽니다.

### 7. P2 안전계수 최종값
- **0.4** (코드 `Z_DEFAULT`가 최종). README 0.6은 오기.

### 8. 부족 비용 $318, 개당 마진 $68 근거
- 9/16 세션에서 "Job 1개 추가 시 makespan +50.8 → 0.508h × $200k = $102/개, 자재 $80(M1 30 + M2 2×25) → 마진 250−182 = $68, Cu = 250+68 = $318"로 계산한 근사치입니다.
- 저장소의 NEH makespan 표(`ms_table.csv`)로 다시 재면 P1 250→270 Job에서 **0.55h/Job → 잔업 인건비 $110/개**, 마진 약 $60, Cu 약 $310. 보고서에는 **"잔업 인건비 약 $100~110/개, 부족 비용 약 $310~320/개"** 로 쓰는 것이 안전합니다. 결론(임계비율 ≈ 0.91)은 변하지 않습니다.

### 9. EOQ 대신 MRP를 쓴 이유
- 서술("자재 소요가 요일마다 달라서")은 맞지만 부수적입니다. 더 큰 이유 두 가지를 앞에 두는 것을 권합니다.
  1. **리드타임이 길어(M2 8일) 발주 "시점"이 핵심**인데 EOQ는 양만 정하고 시점은 재주문점에 맡김 → 재주문점 방식이 바로 AUTO의 결품 구조.
  2. **라운드가 끝나면 남는 자재가 전액 매몰**이라 EOQ의 상시 재고가 손해. MRP는 종료일 기준으로 딱 맞춰 끝낼 수 있음.
- EOQ는 버린 게 아니라 **발주 1회의 커버 기간(요청 10)을 정하는 데** 사용했습니다.

### 10. 커버 기간 M1·M2 3일, M3 5일 근거
- EOQ 주기 T* = √(2S/(H·D)) (일 단위): M1 √(2×1M/(1×250k×5/7)) ≈ 3.3일, M2 √(2×3M/(1×656k)) ≈ 3.0일, M3 √(2×2M/(2×78k)) ≈ 5.1일 → 3/3/5일로 반올림. `planner.material_orders(T_int={'M1':3,'M2':3,'M3':5})`.

### 11. P1을 미리 생산하지 않는 규칙
- 서술 맞습니다. 수치 보강: P1 하루치 25만 개를 하루 보관하면 $7.5M > 작업준비비 $5M. 요일별 makespan 차이(1~2%)로는 역전 불가. 코드에서는 `allocate()`에 P1만 `hi = lo`(당일 수요분만)로 고정. 7요일 DP 전수로도 절감 0 확인.

### 12. 할인 정책
- 서술 맞습니다("기본 0%, 완제품 재고 2일치 이상이면 검토"). 한 가지: 초안 2.6의 **"매뉴얼 예시: 판매량 6% 증가"는 제가 본 PDF(IOG_문제소개 p.14)에는 "10% 할인 → 수요 100→110개(+10%)"만 있습니다.** 6%의 출처를 확인해 주세요. 실제 탄력성은 한 번도 실험하지 못했으므로 "매뉴얼 예시 가정" 표현은 유지.

## 4. 코드 이슈

### `planner.allocate()` 빈 dp 오류
- **재현했습니다** (`inv0=700 Job, 주간 수요 560 Job` → `ValueError: min() arg is an empty sequence`). 원인: 남은 수요가 재고보다 적으면 `hi = need + remaining − s`가 `lo`보다 작아져 전이가 없음. 수정은 `hi = max(lo, …)`로 x=0 전이를 허용하는 한 줄입니다. R2602C 전에 고쳐서 올리겠습니다(README의 P2 0.4, 데이터 갱신 방법과 함께).

### 로컬 사본의 수요 데이터 갱신
- 맞습니다. `daily_run.py`의 스케줄러 등록은 제 PC에만 있습니다. 다른 PC에서는
  `python daily_check.py --round R2602C --start 2026-11-01 --end 2026-12-04`
  를 실행하면 `data/demand_*.csv`와 공개 보드가 갱신됩니다(`--no-fetch`를 붙이지 않으면 항상 받음). README에 "planner 실행 전 반드시 이 명령으로 갱신" 절차를 추가하겠습니다. R2602C 운영 때는 **입력 담당 PC에서 매일 16시 이후 이 명령 → planner** 순서로 고정하면 됩니다.
